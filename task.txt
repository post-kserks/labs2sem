Семинар 4: Полиморфизм в C++. Динамическое связывание и гибкость архитектуры

 1. Теоретическая часть

 1.1. Определение полиморфизма

Полиморфизм — это способность объектов с одинаковым интерфейсом иметь разную реализацию. В контексте объектно-ориентированного программирования полиморфизм позволяет единообразно обращаться с объектами разных классов, входящих в одну иерархию, не заботясь об их конкретном типе.

Если на предыдущем семинаре основное внимание уделялось тому, как строить иерархии классов с использованием наследования, то теперь акцент смещается на то, как этими иерархиями управлять. Полиморфизм делает архитектуру гибкой: новый тип данных можно добавить, не изменяя код, который этими данными оперирует. Это соответствует принципу открытости/закрытости  (Open/Closed Principle) из SOLID

1.2. Статический полиморфизм и динамический полиморфизм

В C++ существуют две основные формы полиморфизма.

·             Статический полиморфизм проявляется на этапе компиляции. К нему относятся перегрузка функций — когда несколько функций имеют одинаковое имя, но разный набор параметров, и компилятор сам выбирает нужную, глядя на типы аргументов. Сюда же относятся шаблоны классов и функций, которые позволяют писать код, работающий с разными типами данных. Решения о том, какой код будет выполнен, принимаются компилятором заранее.

·             Динамический полиморфизм работает во время выполнения программы. Его суть в том, что вызов метода определяется не типом переменной, объявленной в коде, а фактическим типом объекта, на который эта переменная ссылается. Это позволяет, например, передавать в функцию объекты разных классов-наследников, и каждый раз будет вызываться свой вариант метода. Динамический полиморфизм реализуется с помощью механизма виртуальных функций.

1.3. Механизм реализации: виртуальные функции

Чтобы в C++ заработал динамический полиморфизм, метод в базовом классе объявляется с ключевым словом virtual. Это указывает компилятору, что производные классы могут переопределить этот метод под свои нужды.

class Student {

public:

    virtual void Speak() const {

        std::cout << "Some student speak\n";

    }

};

 

Когда класс содержит хотя бы одну виртуальную функцию, компилятор создаёт для него специальную таблицу — виртуальную таблицу, или VTable. В этой таблице хранятся адреса виртуальных функций класса. Каждый объект такого класса получает скрытый указатель на эту таблицу. Когда вызывается виртуальный метод, программа обращается к этому указателю, находит нужную функцию в таблице и выполняет её. Благодаря этому вызов направляется к правильной реализации — той, которая принадлежит фактическому типу объекта.

Современный C++ рекомендует использовать спецификатор override в производных классах. Он явно указывает, что метод переопределяет виртуальную функцию из базового класса. Если в базовом классе нет метода с такой сигнатурой, компилятор выдаст ошибку, что помогает вовремя заметить опечатки или несоответствия.


class Student_IU5 : public Student {

public:

    void Speak() const override {

        std::cout << "Hi!\n";

    }

};

Для запрета дальнейшего переопределения можно использовать 
final
:

class Student_IU5_Iu5_21B : public Student_IU5 {

public:

    void Speak() const final {  // дальнейшее переопределение запрещено

        std::cout << "Hi!\n";

    }

};

 

1.4. Абстрактные классы и интерфейсы

 

В реальных проектах часто оказывается, что объект базового класса не имеет смысла сам по себе. Например, сущность «Издание» без конкретного типа — это абстракция, а не реальный объект. В таких случаях базовый класс делают абстрактным.

 

Абстрактным класс называется, если в нём объявлена хотя бы одна чистая виртуальная функция. Такая функция помечается присваиванием нуля (=0). Она не имеет реализации в базовом классе и обязывает каждый производный класс предоставить свою реализацию.

class Publication {

public:

    virtual void printInfo() const = 0;      // чистая виртуальная функция

    virtual int getLoanPeriod() const = 0;   // чистая виртуальная функция

   

    virtual ~Publication() = default;        // виртуальный деструктор

};

Класс, содержащий чистые виртуальные функции, нельзя инстанцировать — нельзя создать его объект.

Такой абстрактный класс часто называют интерфейсом. Он задаёт контракт: любой наследник обязуется реализовать определённый набор методов. Это позволяет писать код, который работает с интерфейсом, не завися от конкретных реализаций.

 

1.5. Виртуальный деструктор

 

При использовании полиморфизма объекты производных классов часто уничтожаются через указатель на базовый класс.

Student* student = new Student("Lepehin_I");

delete student;  // если деструктор не виртуальный, то вызовется только ~Student()
 

Если деструктор базового класса не объявлен виртуальным, то при удалении будет вызван только деструктор базового класса, а деструктор производного — нет. Это приводит к тому, что ресурсы, выделенные в производном классе, не освобождаются, и возникают утечки памяти.

 

Правило: если класс предназначен для того, чтобы быть базовым и содержать виртуальные методы, его деструктор обязательно должен быть виртуальным. Для полиморфных базовых классов это требование является обязательным.

class Student {

public:

    virtual ~Student () = default;  // виртуальный деструктор

};

2. Практическое задание

 

Цель работы: Модифицировать структуру классов, созданную на первом семинаре, добавив в неё полиморфное поведение. Это позволит закрепить понимание динамического связывания, виртуальных функций и абстрактных классов.

 

Задание:

Необходимо взять реализацию выбранного варианта предметной области из списка, выполненную на предыдущем семинаре. Список вариантов предметных областей (от 1 до 30) и требования к наличию наследования, ассоциации, агрегации, композиции и делегирования остаются полностью неизменными.

 

Дополнительные требования, связанные с полиморфизмом:

 

1. Создание абстрактного интерфейса

·         Определите абстрактный базовый класс, который будет служить интерфейсом для вершины вашей иерархии или для отдельной важной сущности предметной области.

·         Этот интерфейс должен содержать минимум две чистые виртуальные функции, отражающие ключевое поведение объектов данной предметной области.

·       Добавьте виртуальный деструктор в интерфейс.

 

2. Иерархия наследования с переопределением

·         Убедитесь, что ваша иерархия наследования, содержащая не менее трёх классов, реализует этот интерфейс.

·         Во всех производных классах при переопределении методов интерфейса используйте ключевое слово override. Это позволит компилятору проверить корректность переопределения.

3. Демонстрация полиморфного поведения

·         Напишите функцию, которая принимает в качестве параметра ссылку или указатель на базовый класс (интерфейс).

·         Внутри этой функции вызовите виртуальные методы. Продемонстрируйте, что один и тот же код корректно работает с объектами разных производных классов, вызывая их специфические реализации.

4. Полиморфное хранение и управление объектами

·        Создайте контейнер (например, 
std::vector
), который хранит объекты ваших классов. Объекты должны храниться через сохраняться через умные указатели на базовый класс (
std::unique_ptr<Base>
 или 
std::shared_ptr<Base>
). Это обеспечит автоматическое управление временем жизни и корректное освобождение памяти.

·        Продемонстрируйте добавление в контейнер объектов различных производных классов и последующий перебор контейнера с вызовом виртуальных методов для каждого объекта.

·         Обеспечьте корректное освобождение памяти при уничтожении объектов — это достигается наличием виртуального деструктора в базовом классе.

·         Продемонстрируйте использование операции приведения типов  (
dynamic_cast
, 
typeid
) для проверки фактического типа объекта во время выполнения. Объясните, в каких ситуациях это может потребоваться (например, для доступа к специфическим методам, отсутствующим в интерфейсе) и почему избыточное использование таких проверок часто свидетельствует о нарушении принципа подстановки Лисков (Liskov Substitution Principle) и неоптимальной архитектуре.

3. Пример выполнения (на примере предметной области «Библиотека»)

 

На предыдущем семинаре для предметной области «Библиотека» была разработана иерархия классов: базовый класс «Издание» и производные от него «Книга», «Журнал», «Газета». Также были реализованы отношения композиции (библиотека состоит из читальных залов), агрегации (читатель имеет список взятых изданий) и делегирования (поиск изданий делегируется каталогу).

На текущем  семинаре эта структура дополняется полиморфизмом.

 

Шаг 1. Создание интерфейса.

Вместо того чтобы делать базовый класс «Издание» конкретным, его превращают в абстрактный интерфейс, который задаёт обязательное поведение для всех типов изданий. Этот интерфейс содержит чистые виртуальные методы, например, «вывести информацию об издании» и «получить срок выдачи». Теперь создать объект «Издание» напрямую невозможно — это логично, так как в библиотеке всегда есть конкретный тип документа.

 

Шаг 2. Реализация интерфейса в иерархии.

Классы «Книга», «Журнал» и «Газета» наследуются от этого интерфейса и реализуют его методы. Для книг срок выдачи составляет, например, 30 дней, для журналов — 7 дней, для газет — 1 день. Каждый класс переопределяет метод вывода информации, добавляя свои специфические поля: количество страниц для книги, номер выпуска для журнала и так далее. Во всех переопределениях используется ключевое слово override.

 

Шаг 3. Полиморфная функция.

Создаётся свободная функция, которая принимает ссылку на интерфейс издания. Внутри этой функции вызываются виртуальные методы: сначала выводится информация об издании, затем сообщается срок выдачи. Эта функция не знает, какой именно объект ей передан — книгу, журнал или газету. Она просто работает с интерфейсом, и благодаря полиморфизму для каждого типа вызывается правильная реализация.

 

Шаг 4. Полиморфное хранение в библиотеке.

В классе «Библиотека» создаётся контейнер, который хранит указатели на интерфейс издания. В такой контейнер можно добавлять любые объекты — книги, журналы, газеты — через умные указатели, что гарантирует автоматическое управление временем жизни. Метод отображения всего фонда просто перебирает этот контейнер и для каждого элемента вызывает полиморфную функцию вывода информации. Таким образом, если в будущем в библиотеку добавится новый тип изданий, например, «Электронная книга», код отображения менять не потребуется — он автоматически начнёт работать с новым типом.

 

Шаг 5. Виртуальный деструктор.

В интерфейс издания добавляется виртуальный деструктор. Это гарантирует, что при удалении объекта «Книга» через указатель на интерфейс будут корректно освобождены все ресурсы, выделенные как в базовой части, так и в части, специфичной для книги.
