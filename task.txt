Часть 1. Теоретический материал

Метрики ООП — это количественные показатели, которые помогают оценить различные аспекты объектно-ориентированного дизайна: сложность, связность, зависимость между классами, качество наследования и другие характеристики.

Метрики позволяют:

- Обнаружить потенциальные проблемы на ранних этапах разработки

- Сравнивать различные варианты проектирования

- Отслеживать ухудшение качества кода со временем

- Обоснованно принимать решения о рефакторинге

1.2. Базовые метрики

Прежде чем переходить к сложным метрикам, рассмотрим простейшие количественные характеристики:

WMC(Weighted Methods per Class) - Суммарная сложность методов клас

DIT(Depth of Inheritance Tree) - Глубина дерева наследования (Максимальная длина цепочки наследования от корня до класса)

NOC (Number of Children) - Количество потомков (Число непосредственных наследников класса)

CBO (Coupling Between Objects) - Сцепление между объектами (Количество классов, с которыми данный класс связан (использует, вызывает)

RFC (Response For a Class) - Множество реакций класса (Количество методов, которые могут быть вызваны в ответ на сообщение объекту)

LCOM (Lack of Cohesion of Methods) (Несвязность методов (Насколько методы класса используют общие поля данных) LCOM > 1 - класс, вероятно, следует разделить на несколько

1.3. Метрики Абреу (MOOD - Metrics for Object Oriented Design)

Жозе Абреу (1995-1999) предложил набор из 6 метрик для количественной оценки характеристик ООП на уровне всей системы:

1.3.1. MIF (Method Inheritance Factor) — фактор наследования методов

MIF = (сумма по всем классам отношения числа унаследованных методов к общему числу методов) / общее количество классов (Доля всех методов системы составляют унаследованные методы)

-  Низкий MIF  → наследование используется слабо, возможно дублирование кода

-  Высокий MIF  → активно используется переиспользование через наследование, но возможно глубокое наследование

1.3.2. AHF (Attribute Inheritance Factor) — фактор наследования атрибутов

AHF = (сумма по всем классам отношения числа унаследованных атрибутов к общему числу атрибутов) / общее количество классов: Доля унаследованных атрибутов.

1.3.3. POF (Polymorphism Factor) — фактор полиморфизма

POF = (сумма по всем классам отношения числа переопределённых методов к общему числу методов) / общее количество классов:  Насколько активно используется полиморфизм в системе.

-  Высокий POF  - сильное использование полиморфизма, гибкая архитектура, но возможно излишнее усложнение

 1.3.4. COF (Coupling Factor) — фактор сцепления

COF = (количество реальных связей между классами) / (количество возможных связей между классами:  Доля возможных связей между классами, которые реально существуют.

-  Высокий COF  → сильно связанная система, трудно тестировать и изменять

-  Низкий COF  → слабая связность, хорошая модульность

1.3.5. MHF (Method Hiding Factor) — фактор сокрытия методов

MHF = (сумма по всем классам числа закрытых методов) / (общее число методов)

Доля скрытых (private/protected) методов.

1.3.6. CHF (Class Hiding Factor) — фактор сокрытия атрибутов

CHF = (сумма по всем классам числа закрытых атрибутов) / (общее число атрибутов)

Доля скрытых атрибутов — показатель качества инкапсуляции

 1.5. Метрики Чидамбера-Кемерера (CK Metrics)

Шридхар Чидамбер и Крис Кемерер  (1994) предложили один из самых известных наборов метрик для ООП, получивший широкое распространение в индустрии:

1.5.1. WMC (Weighted Methods per Class)

-  Высокий WMC  - класс сложнее для понимания, тестирования и поддержки

-  Низкий WMC  - класс простой, лёгкий в переиспользовании

  Пороговые значения:  WMC ≤ 20-30

    1.5.2. DIT (Depth of Inheritance Tree)

 -  Большой DIT  - больше переиспользования, но выше сложность, глубже может нарушаться инкапсуляция

  Пороговые значения:  DIT ≤ 5 (по Лоренцу-Кидду)

  1.5.3. NOC (Number of Children)

-  Большой NOC  - родительский класс может быть перегружен обязанностями, изменения в нём затронут много наследников

   1.5.4. CBO (Coupling Between Objects)

 -  Высокий CBO  → высокая связанность, низкая переиспользуемость, сложность тестирования

  Пороговые значения:  CBO ≤ 12-15

 1.5.5. RFC (Response For a Class)

 -  Большой RFC  → сложность тестирования, больше возможных ошибок

  Пороговые значения:  RFC ≤ 50

  1.5.6. LCOM (Lack of Cohesion of Methods)

-  LCOM > 1  → класс слабо связный, вероятно, следует разделить

-  LCOM = 0  → идеальная связность (но редко достижимо)

-  LCOM в норме  → 0-1

   2.3. Расчёт системных метрик MOOD (Абреу)

 Для расчёта сначала соберём общие данные по системе:

 -  Общее количество классов (TC)  = 4 (Издание, Книга, Журнал, Газета)

     2.3.1. MIF (Method Inheritance Factor)

 Рассчитаем для каждого класса отношение числа унаследованных методов к общему числу методов:

     Класс        Унаследованные методы     Всего методов     Отношение    

     Издание     0                                             3                           0,00    

    Книга           2                                             5                           0,40    

    Журнал        2                                             5                           0,40    

    Газета           2                                             4                          0,50    

  Сумма отношений  = 0,00 + 0,40 + 0,40 + 0,50 =  1,30

  MIF = 1,30 / 4 = 0,325

  32,5% методов системы являются унаследованными — умеренное использование наследования, что является хорошим показателем.

     2.3.2. AHF (Attribute Inheritance Factor)

     Класс     Унаследованные атрибуты     Всего атрибутов     Отношение    

    Издание     0                                                 0                               0,00    

    Книга          0                                                 3                               0,00    

    Журнал      0                                                 2                               0,00    

    Газета        0                                                  2                               0,00    

  Сумма отношений  = 0,00

  AHF = 0

  Атрибуты не наследуются, так как все они определены в конкретных классах, а базовый класс не имеет атрибутов. Это соответствует принципу: интерфейс не должен диктовать реализацию.

     2.3.3. POF (Polymorphism Factor)

 Рассчитаем для каждого класса число переопределённых методов:

   Класс     Переопределённые методы     Всего методов     Отношение    

   Издание     0 (базовый)                                3                             0,00    

    Книга         2                                                   5                              0,40    

    Журнал     2                                                    5                             0,40    

    Газета       2                                                    4                              0,50    

  Сумма отношений  = 0,00 + 0,40 + 0,40 + 0,50 =  1,30

  POF = 1,30 / 4 = 0,325

 32,5% методов переопределены. Это достаточно высокий показатель, свидетельствующий об активном использовании полиморфизма.

 2.3.4. COF (Coupling Factor)

 Определим связи между классами (направление не важно, учитываем уникальные пары):

    Пара классов              Наличие связи 

   Издание — Книга         Да (наследование)    

    Издание — Журнал     Да (наследование)    

    Издание — Газета       Да (наследование)    

    Книга — Журнал         Нет    

    Книга — Газета           Нет    

    Журнал — Газета       Нет    

  Количество реальных связей  = 3

  Количество возможных связей  = (4 × 3) / 2 = 6 (число пар)

  COF = 3 / 6 = 0,50

   50% возможных связей реализованы — довольно высокое сцепление. Это связано с тем, что все три наследника связаны с базовым классом.

  2.5. Общий вывод

 Архитектура системы «Библиотека» характеризуется:

 -  Низкой глубиной наследования  — все классы находятся на первом уровне наследников; это упрощает понимание и модификацию кода.

-  Малой сложностью классов  — каждый класс содержит 2-5 методов, что соответствует принципу единственной ответственности.

-  Умеренным использованием полиморфизма  — более 30% методов переопределены, что даёт гибкость без излишнего усложнения.

-  Высоким сцеплением на верхнем уровне  — все наследники связаны с базовым классом; это неизбежно для иерархий, но не является критичным для системы такого размера.

  Итоговая оценка качества:  архитектура признаётся  хорошей  с потенциалом для небольших улучшений (вынос общего атрибута в базовый класс)
