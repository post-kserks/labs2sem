# Отчёт по семинару №6

**Тема:** Очередь отложенных вызовов функций и методов классов  
**Предметная область:** Школа (классы из предыдущих семинаров)  
**Язык реализации:** C++17  
**Сборка и запуск:** `make`, `make run`

---

## 1. Цель работы

Целью семинара является освоение механизма отложенного выполнения произвольных функций и методов классов с помощью вариадических шаблонов, полиморфизма и стандартных средств C++ (`std::tuple`, `std::apply`, `std::queue`).

Практическая задача — реализовать очередь, которая позволяет:

- добавлять в неё вызовы с произвольным числом аргументов разных типов;
- выполнять сохранённые вызовы по одному или все сразу;
- применить этот механизм к объектам предметной области «школа».

---

## 2. Задачи

В рамках работы необходимо было решить следующие задачи:

1. Реализовать базовый интерфейс отложенного вызова `IPending` с единственным методом `run()`.
2. Реализовать шаблонный класс `Pending<Callable, Args...>`, сохраняющий callable-объект и его аргументы.
3. Реализовать класс `PendingQueue` с методами:
   - `enqueue` — добавление отложенного вызова;
   - `run_one` — выполнение одного вызова из начала очереди;
   - `run_all` — последовательное выполнение всех вызовов.
4. Продемонстрировать работу очереди на примерах из предметной области:
   - отложенный вызов свободной функции;
   - отложенный вызов метода класса.
5. Обеспечить сборку проекта через `Makefile` и возможность просмотра структуры проекта командой `make structure`.

## 4. Основная часть

### 4.1. Постановка проблемы

Очередь отложенных вызовов должна хранить функции и методы с **разным количеством и типами аргументов**. На этапе добавления в очередь заранее неизвестно, какой именно вызов будет сохранён: это может быть `printf`, метод `School::addTeacher` или `MyContainer::push_back`.

Прямое хранение указателей на функции с фиксированной сигнатурой не подходит — теряется гибкость. Поэтому выбран подход из методических указаний: полиморфный базовый класс + шаблонная реализация для каждой конкретной комбинации callable и аргументов.

### 4.2. Архитектурное решение

#### Интерфейс `IPending`

Базовый абстрактный класс определяет единственный контракт — метод `run()`. Очередь работает исключительно с указателями на `IPending`, не зная деталей конкретного вызова.

**Обоснование:** это реализация принципа инверсии зависимостей (DIP) — `PendingQueue` зависит от абстракции, а не от конкретных функций. Также соблюдается принцип разделения интерфейсов (ISP): интерфейс минимален и содержит только то, что необходимо для выполнения вызова.

#### Шаблон `Pending<Callable, Args...>`

Класс наследует `IPending` и хранит:

- `_callable` — указатель на функцию, указатель на метод или другой вызываемый объект;
- `_args` — кортеж аргументов типа `std::tuple<Args...>`.

При вызове `run()` аргументы распаковываются через `std::apply`, что позволяет передать их в callable «как есть», без ручного перечисления.

**Обоснование:** вариадический шаблон автоматически выводит типы аргументов при вызове `enqueue`, поэтому пользователю очереди не нужно явно указывать сигнатуру. Каждая комбинация `(Callable, Args...)` получает собственную специализацию `Pending`, что обеспечивает типобезопасность на этапе компиляции.

#### Класс `PendingQueue`

Очередь наследуется от `std::queue<std::unique_ptr<IPending>>` (приватное наследование), что скрывает внутреннюю реализацию и предоставляет наружу только необходимые методы.

| Метод | Назначение |
|-------|------------|
| `enqueue(callable, args...)` | Создаёт объект `Pending`, оборачивает в `unique_ptr`, помещает в очередь |
| `run_one()` | Выполняет первый элемент и удаляет его |
| `run_all()` | Последовательно вызывает `run_one()` до опустошения очереди |

В деструкторе выводится предупреждение, если в очереди остались невыполненные вызовы — это помогает обнаружить утечку логики (забыли вызвать `run_all`).

**Обоснование:** приватное наследование от `std::queue` не даёт клиенту напрямую манипулировать внутренним контейнером, сохраняя инкапсуляцию. Использование `std::unique_ptr` обеспечивает автоматическое освобождение памяти.

### 4.3. Соответствие принципам SOLID

| Принцип | Реализация в проекте |
|---------|----------------------|
| **S** (Single Responsibility) | `Pending` отвечает за один вызов, `PendingQueue` — за управление очередью, `Demo` — за демонстрацию |
| **O** (Open/Closed) | Новые типы вызовов добавляются через `enqueue` без изменения кода очереди |
| **L** (Liskov Substitution) | Любой `Pending<...>` может использоваться через интерфейс `IPending` |
| **I** (Interface Segregation) | `IPending` содержит единственный метод `run()` |
| **D** (Dependency Inversion) | Очередь оперирует абстракцией `IPending`, а не конкретными функциями |

### 4.4. Демонстрация на предметной области

В файле `Demo.cpp` реализован сценарий, имитирующий рабочий день школы. В очередь добавляются семь отложенных вызовов:

| № | Вызов | Тип |
|---|-------|-----|
| 1 | `printf("Hello, %s\n", "world")` | Стандартная C-функция |
| 2 | `printMessage("Школа готовится...")` | Свободная функция предметной области |
| 3 | `addTeacherLogged(&school, ivan)` | Метод класса `School` |
| 4 | `addTeacherLogged(&school, maria)` | Метод класса `School` |
| 5 | `pushBackLogged(&staff, Teacher(...))` | Метод шаблонного класса `MyContainer` |
| 6 | `&Student::study` | Const-метод класса `Student` |
| 7 | `&School::conductLessons` | Метод без дополнительных аргументов |

#### Важные технические решения в демонстрации

**1. Использование `std::ref` для ссылочных аргументов**

При передаче объекта `Teacher` в `enqueue` без `std::ref` аргумент копируется в `std::tuple`. Метод `addTeacher` получает ссылку на копию внутри объекта `Pending`. После выполнения `run_one()` этот объект уничтожается, и указатель в `School::teachers` становится невалидным.

Решение — оборачивание аргумента в `std::ref(ivan)`, чтобы в кортеже хранилась ссылка `Teacher&` на исходный объект, живущий на стеке `runPendingQueueDemo()`.

**2. Обёртки `addTeacherLogged` и `pushBackLogged`**

Методы `School::addTeacher` и `MyContainer::push_back` не выводят информацию в консоль — они только изменяют внутреннее состояние. При пошаговом выполнении `run_one()` создаётся впечатление, что «пустые» шаги не работают, хотя вызовы выполняются корректно (что подтверждается последующим выводом `conductLessons` и содержимого `MyContainer`).

Для наглядности демонстрации созданы обёртки, которые вызывают исходный метод и дополнительно печатают сообщение о результате. Это не меняет логику очереди, а лишь улучшает наблюдаемость поведения программы.

**3. Разделение `main.cpp` и `Demo.cpp`**

Точка входа (`main.cpp`) содержит только вызов `runPendingQueueDemo()`. Вся демонстрационная логика вынесена в отдельный модуль, что соответствует принципу единственной ответственности и упрощает сопровождение кода.

### 4.5. Сборка проекта

`Makefile` компилирует три единицы трансляции: `main.cpp`, `Demo.cpp`, `School.cpp`. Заголовочные файлы (включая шаблонные) подключаются через `#include`. Стандарт C++17 выбран как минимально необходимый для `std::apply`.

Доступные команды:

- `make` — сборка исполняемого файла `school_app`;
- `make run` — сборка и запуск;
- `make structure` — вывод структуры проекта;
- `make clean` — удаление объектных файлов и бинарника.

## 6. Вывод

В ходе работы была реализована очередь отложенных вызовов `PendingQueue`, соответствующая требованиям семинара №6. Механизм построен на сочетании полиморфизма (`IPending`), вариадических шаблонов (`Pending<Callable, Args...>`) и стандартной очереди C++.

Ключевые результаты:

- очередь принимает произвольные функции и методы с любым числом аргументов;
- вызовы выполняются строго в порядке добавления (FIFO);
- механизм успешно интегрирован с классами предметной области «школа» из предыдущих семинаров;
- архитектура соответствует принципам SOLID и обеспечивает расширяемость без модификации существующего кода очереди.

В процессе отладки был выявлен и устранён нюанс с копированием аргументов в `std::tuple` (необходимость `std::ref` для ссылочных типов), а также улучшена наглядность демонстрации за счёт обёрток с логированием для «молчаливых» методов.

Проект собирается одной командой `make` и готов к демонстрации на защите.
